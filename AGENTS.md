# AGENTS.md

## Purpose

This repo holds Paulo's config for his Fedora Linux workstations — plural.
Every machine runs the same stack (Niri + DankMaterialShell, kitty, Neovim,
herdr, cava, zsh), and the same checkout is used on all of them: a desktop
with an external ultrawide, a laptop, and whatever comes next.

**Everything committed here must work on every machine.** Before changing or
committing a setting, ask: would this be wrong on a different machine? If yes,
it doesn't belong in git (see [Per-machine settings](#per-machine-settings)).

## Layout

| Repo path            | Lives at                  | How                    |
| -------------------- | ------------------------- | ---------------------- |
| `dot_config/<tool>/` | `~/.config/<tool>`        | directory symlink      |
| `dot_gitconfig`      | `~/.gitconfig`            | symlink                |
| `zsh_functions.zsh`  | sourced from `~/.zshrc`   | `source` line          |
| `zsh_aliases.zsh`    | sourced from `~/.zshrc`   | `source` line          |
| `dot_tmux`, `dot_tmux.conf` | `~/.tmux`, `~/.tmux.conf` | symlink (legacy) |

The `dot_` prefix is only a naming convention; this repo does not use chezmoi.
Because `~/.config/<tool>` *is* the repo directory, anything a tool writes
into its config folder shows up in `git status` here.

### Setting up a machine

```sh
./install.sh --dry-run   # show what would change
./install.sh             # link everything, append the zshrc source lines
```

`install.sh` is idempotent: correct links are left alone, and anything in the
way is moved to `<name>.backup-<timestamp>`, never deleted. Every directory
under `dot_config/` is linked automatically.

### Adding a new tool

1. Move its folder into `dot_config/<tool>` and run `./install.sh`. Don't hand-roll
   `ln -s` into an existing directory — that's how a stray self-link
   (`dot_config/cava/cava -> cava`) once got committed.
2. If the tool keeps runtime state next to its config (sockets, logs, caches,
   session files), add a `.gitignore` inside the tool's folder that ignores
   everything except the real config. `dot_config/herdr/.gitignore` is the
   pattern to copy.
3. Check the tool's config for anything machine-specific before committing.

## Per-machine settings

Displays, monitor names (`DP-3`, `eDP-1`), resolutions, scale, refresh rates,
input devices, hostnames and absolute hardware paths differ between machines
and must not be committed.

- Keep per-machine values in a separate file that the shared config
  `include`s, and gitignore that file. Current per-machine files:
  - `dot_config/niri/dms/outputs.kdl` — display layout (written by DMS)
  - `dot_config/DankMaterialShell/plugin_settings.json` — DMS plugin config
    (Home Assistant address, world clock cities). `install.sh` seeds it from
    the committed `plugin_settings.example.json`; keep the example free of
    personal values.
- niri refuses to load a config whose `include` target is missing, so
  `install.sh` creates empty placeholders for gitignored include targets.
  Add any new one there too.
- Don't put `output` blocks in `dot_config/niri/config.kdl`.

## Generated files

DankMaterialShell regenerates these from the current wallpaper/theme. They are
gitignored; never hand-edit or commit them:

- `dot_config/niri/dms/colors.kdl`
- `dot_config/kitty/dank-theme.conf`, `dot_config/kitty/dank-tabs.conf`
- `dot_config/DankMaterialShell/firefox.css`, `zen.css`

The other files in `dot_config/niri/dms/` marked "DO NOT EDIT / generated by
DMS" (layout, binds, cursor, alttab, input, windowrules, …) are written by the
DMS settings UI but hold real preferences, so they *are* committed. Change them
through DMS rather than by hand, and still check them for per-machine values.

`dot_config/nvim/lua/plugins/dankcolors.lua` started as DMS output but has been
hand-edited (disabled in favor of the bru colorscheme), so it is tracked.

## Secrets and personal data

This repo is public on GitHub. Never commit tokens, API keys, passwords or private
keys. When a config needs a secret, point it at a file outside the repo (the
Home Assistant plugin reads `~/.home-assistant-token`, for example) and leave
the inline field empty. Before committing, scan the staged diff for secrets
and for personal details such as home server URLs and locations.

## Commits

- One commit per tool or topic (herdr, niri + DMS, kitty, nvim, …); don't
  sweep unrelated changes into a commit.
- Commit only the paths you mean to (`git commit -- <paths>`); other entries
  may already be staged. Careful: `git commit -- <path>` commits the
  *working-tree* file, so it silently undoes a `git rm --cached <path>`. To
  untrack a file, commit from the index (plain `git commit` with only the
  intended changes staged) instead.
- Third-party code cloned into the tree (e.g. DMS plugins under
  `dot_config/DankMaterialShell/plugins/`) is added as a git submodule
  (`git submodule add <url> <path>`), never as plain files. `install.sh` runs
  `git submodule update --init`.

## Legacy

Kept but not maintained; don't build on these:

- tmux + tmux-powerline (`dot_tmux*`, `dot_config/tmux-powerline`) — herdr
  replaced it. The tmux versions of the zsh helpers survive as `tcode`, `twh`
  and `tnocode`.
- `dot_vimrc` (Vundle), `dot_ackrc` — not linked by `install.sh`.
- `gnome/` — from before the switch to Niri.
- The macOS-isms in `zsh_aliases.zsh` (e.g. `ls -G`).
